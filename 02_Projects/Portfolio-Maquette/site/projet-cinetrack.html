CinéTrack

Application de suivi de films : recherche, fiches détaillées, listes « vus » et « à voir », critiques.

AngularSignalsRxJSPrimeNGAPI TMDB
Voir la démo ↗ Code source

01Contexte et problème

Entre les plateformes de streaming, les recommandations d'amis et les notes éparpillées, il est difficile de savoir ce qu'on a déjà vu et ce qu'on veut voir. CinéTrack centralise tout : on cherche un film, on l'ajoute à une liste, on laisse un avis.

Objectif : une application rapide, utilisable au clavier et sur mobile, qui reste fluide même avec des centaines de films.

02Fonctionnalités

🔎 Recherche instantanéeRésultats pendant la frappe, sans requêtes inutiles.
🎬 Fiches détailléesCasting, bande-annonce, films similaires.
📋 Listes personnelles« Vus », « À voir », favoris, persistés.
⭐ CritiquesNote et avis, avec validation des champs.

Organisation core / shared / features : chaque fonctionnalité contient sa couche d'accès aux données (DTO → mapper → modèle), son store et ses composants d'affichage. Les pages ne parlent jamais directement à l'API.

04Choix techniques

ChoixPourquoi
Signals + OnPushRendu ciblé : seuls les composants concernés se mettent à jour.
RxJS (switchMap, debounce)Recherche pendant la frappe sans requêtes en double ni résultats dans le désordre.
Mapper DTO → modèleLe reste de l'app ne dépend pas du format de l'API TMDB.
PrimeNGComposants accessibles prêts à l'emploi, pour me concentrer sur la logique.
@deferLes blocs lourds (bande-annonce, similaires) ne se chargent qu'à l'affichage.

05Difficultés et solutions

Résultats de recherche dans le désordre

Une réponse lente pouvait écraser une réponse plus récente.

switchMap annule la requête précédente : seule la dernière frappe compte.

Limite de requêtes de l'API

Des appels répétés sur les mêmes fiches consommaient le quota.

Cache en mémoire par identifiant et debounceTime(300) sur la recherche.

Clé d'API exposée

Une clé présente dans le code front est visible par tout le monde.

Appels via un proxy côté serveur (CinéTrack API) : la clé ne quitte jamais le serveur.

06Sécurité et qualité

  • Aucune clé secrète dans le front : proxy côté serveur.
  • Contenu externe affiché sans innerHTML : pas de faille XSS.
  • Intercepteur HTTP central pour les erreurs et les jetons.
  • Tests unitaires des stores et mappers, tests E2E du parcours principal, pipeline CI obligatoire avant fusion.

08Ce que j'en retiens

  • Séparer données et affichage rend les changements d'API presque indolores.
  • Les signals simplifient l'état local ; RxJS reste le bon outil pour les flux asynchrones.
  • Mesurer (Lighthouse, tests) avant d'optimiser évite de travailler à l'aveugle.
